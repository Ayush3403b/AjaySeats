# Internationalisation (English and Hindi)

- Translations live in `apps/web/src/i18n/locales/en.json` and `hi.json`. Keys are nested by feature (`catalogue.filters.material`).
- `en.json` and `hi.json` must have identical key sets. `src/i18n/locales.test.ts` enforces this, and also fails on empty strings.
- Language is resolved in this order: `?lang=` query parameter, then the stored choice, then English. The header toggle updates both.
- Bilingual data from the API (`{ en, hi }`) uses `localized()` in `lib/format.ts`, which falls back to English when Hindi is empty.
- Prices use `Intl` with `en-IN` or `hi-IN` locale, through `formatInr` in `packages/shared`.
- Form validation messages are translation keys. The schema stores keys, and the form translates them at render time. Server validation messages are shown as returned (English) because they are not translation keys.
- Legal pages (`legal.privacy.sections`, `legal.terms.sections`) are arrays of `{ h, p }` in both languages. They are marked as drafts for owner review and need legal review before publication.

To add a string: add the key to both files, then use `t('your.key')`. Run `npm test -w @pcs/web`.

## Admin strings

All admin screens use the `admin.*` namespace in both `en.json` and `hi.json`. The key sets must match; `locales.test.ts` fails if they drift.

- API error codes map to `admin.errors.<CODE>` through the `KNOWN` list in `apps/web/src/admin/messages.ts`. A new API error code needs a `KNOWN` entry and both locale strings, or it shows the generic message.
- Validation messages from the form schema are translation keys, so they change with the language. Messages returned by the server for a specific field are shown as returned.
- Staff notes written by the admin UI (see `docs/api.md`) are stored in English. They are shown as stored in both languages.
